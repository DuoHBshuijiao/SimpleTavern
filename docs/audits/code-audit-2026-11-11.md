# 代码审查记录（2026-11-11 起）

范围：桌面端仓库的全部代码，不限于近期改动。采用代码检查、隔离实验和浏览器界面操作，没有改业务代码。

做法：先读代码找疑点，再在空数据目录的后端和模拟上游上做对照实验；第 34 轮开始用 computer-use 插件补实际浏览器操作。标“已确认”的都有能通过的对照；标“未复现”的只是读代码得出，不能当结论。

## 作者的决定（2026-11-11）

- 生成中应该允许切换会话。
- 多个会话同时处于生成状态应该是允许的。
- 助手覆盖已有的工作区文件算破坏性操作，要打开破坏性开关（见第 9 项）。

现状和这两条不符，见第 3 项和“多会话同时生成”一节。

## 已确认

### 1. 生成期间对会话的修改，在回复结束时被整份回滚（丢数据）

- 现象：回复流式输出期间改标题、写长期记忆，回复结束后标题变回原样，长期记忆文件被删。对照：同样的修改在没有生成时做，全部保留。
- 原因：`routes/generate.py` 的 `generate_stream` 在请求开始时 `load_chat`，结束时 `_persist_generation_record` 把这份旧副本整份 `save_chat`。会话没有读改写保护，`storage.py` 的锁只保护单次读或单次写。
- 同一路径上按代码也会被覆盖、但没有逐个复现的：助手自动总结写入的长期记忆、MVU 状态更新和 `mvuProcessed` 标记、TTS 音频绑定。

### 2. 生成期间改的全局设置也会被回滚

- 现象：某个模型第一次使用时，回复期间改的全局提示词在回复结束后变回原值。对照：模型已在 `usedModels` 里时不回滚。
- 原因：`_persist_generation_record` 为了更新 `usedModels`，把请求开始时读入的整份设置 `save_settings`。
- 未复现的连带：`save_settings` 会清理不在预设列表里的 OAuth 登录，这期间新建并登录的预设可能被登出。

### 3. 生成中切到别的会话，回复结束时被拉回原会话

- 现象：在会话 A 发送后点开会话 B，回复结束时界面自动跳回 A。
- 原因：`ChatPage.vue` 生成结束的 `finally` 无条件 `chats.load(chatId)`，而 `stores/chats.ts` 的 `load` 会把加载到的会话设为当前会话。
- 按作者决定，这是缺陷：结束时不该切换当前会话。

### 4. 生成中重命名会话，正在输出的气泡消失

- 现象：流式输出时重命名，本地的用户消息和正在生成的回复从界面上消失，回复结束才重新出现；标题随后因第 1 项变回旧名，侧栏仍显示新名。
- 原因：`stores/chats.ts` 的 `rename`（以及 `updateOverrides` 等）用服务器返回的会话替换了带本地流式消息的 `activeChat`。
- 说明：实验是直接调用 store 的 `rename`，没有点界面上的按钮。

### 5. 删除角色后，会话目录删不干净

- 现象：删除带会话的角色后，`data/chats/{角色id}/{会话id}/` 还在，里面剩 `chat.json.lock`、`chat.json.lock.lock` 等 4 个文件。
- 原因：`storage.py` 的 `delete_chats_by_character` 删每个文件前都 `_lock_for`，包括锁文件本身，边删边生成新的锁文件，目录非空删不掉。
- 影响：只是残留，不影响功能。

### 6. 本机接口不校验请求来源

- 现象：带外部域名 `Host` 头的请求能读到 `/api/settings`（含 API Key）；带外部 `Origin` 的表单上传能进入 `/api/import` 的处理逻辑（表单上传不触发 CORS 预检）。`POST /api/update/run` 没有请求体，同样不触发预检，实验里没有调用它。
- `routes/update.py` 的 `download_update` 把 `tagName` 直接拼进下载地址，带 `..` 时 httpx 会规范化成 GitHub 上别的仓库的地址；下载的 zip 之后由更新脚本解压覆盖程序。地址规范化单独验证过，完整的下载和更新没有执行。
- 影响：部署边界是只支持本机，利用要靠恶意网页加 DNS 重绑定，较新的 Chrome 对网页访问本机也有拦截，风险不高。修法：Host 和 Origin 白名单，校验标签格式。

## 未复现（只读代码）

- 生成中切到别的会话再点停止：`persistLocalStreamingMessages` 取的是当前会话的本地消息，半截回复不会保存。
- `PUT /api/chats/{id}` 只传部分 `overrides` 时 `presetId` 被清空（这一点实验确认）：`_merge_overrides` 用 `hasattr` 判断 `presetId`、`contextStartMessageId`、`draftHelp`，对 Pydantic 字段恒为真。前端总是传完整对象，目前不触发。
- `stores/chats.ts` 的 `load` 和 `loadList` 都不丢弃过期响应，和 T-814 里偶发开场白问题的疑点同类。

## 多会话同时生成

现状不支持，要做需要改这几处（读代码得出，除注明外未做实验）：

- 前端只有一个全局的 `isGenerating` 和一个 `aborter`（`ChatPage.vue`）。A 在生成时切到 B，B 的发送按钮显示“停止”（实验中看到），点它停的是 A；B 里不能发送。
- 流式增量只写进 `activeChat`（`stores/chats.ts` 的 `appendLocalMessageContent` 按本地消息 id 在当前会话里找）。切走后增量被丢弃；切回 A 时从服务器加载，本地的流式气泡已经没有，要等结束后才看到回复。
- 思考内容、联网状态、延后删除和重写合并的上下文（`useGenerationDeferState`、`useMainChatReasoning`）都是页面级单例，不分会话。
- 后端三个生成接口是 `async def`，但读写会话、分词、世界书正则都是同步调用，直接跑在事件循环上。一个会话在准备请求时，其他会话的流会停顿；`storage.py` 的 `_acquire_portalock` 等锁时用 `time.sleep` 轮询，最长 30 秒，同样会卡住所有流。
- 第 1、2 项的整份回写在多会话同时生成时更容易触发：两个回复先后结束，后结束的那个会用旧设置覆盖先结束的那个写入的 `usedModels`。

## 第二轮（2026-11-11）

### 7. 正文正则的超时不起作用，一条回溯爆炸的规则会冻住整个后端（已确认）

- 现象：规则 `(a+)+$` 作用在 24 个 `a` 加一个 `b` 上，`apply_content_regex_pipeline` 1.34 秒后才返回 `REGEX_TIMEOUT`（设定是 0.15 秒），期间另一个每 50 毫秒打点的线程一次都没有运行。对照：规则 `a+b` 立即返回。文本每多一个字符耗时翻倍。
- 原因：`content_regex.py` 把正则放进线程池再用 `future.result(timeout=...)` 等待，但 Python 的 `re` 匹配期间不释放 GIL，等待的线程拿不到执行机会；超时后那个线程也停不下来。
- 触发面：规则来自用户、导入的角色卡和助手工具（模型写的）。后台扫描每轮都会对会话跑规则，所以坏规则在每次启动后都会再次触发。真实规则触发的情况没有复现。
- 世界书条目的正则（`routes/generate.py` 的 `match_worldbook_entries`）没有任何超时，并且在事件循环上执行。

### 8. 群聊和插话生成有和第 1 项相同的写法（读代码）

`generate_group_response` 和 `generate_single_interject` 同样在开头 `load_chat`、结尾经 `_persist_generation_record` 整份 `save_chat`。没有单独做实验。

### 未复现（只读代码）

- 本机接口一旦可被调用就等于可执行代码：`/api/tts/glm-local/start` 等接口按设置里的仓库路径用 `powershell -ExecutionPolicy Bypass` 运行脚本，而设置可以通过接口改写。这抬高了第 6 项的后果。
- MVU 正则模式：`mvu_daemon._run_once` 先 `dequeue_by_message_id` 再调用模型，调用失败时队列项不放回；扫描器的 `_processed_signatures` 已记下这条消息，本次进程内不会再入队，这条消息的状态更新会被跳过。
- MVU 后台循环：每个开过 MVU 的会话一个常驻任务，每 5 秒在事件循环上完整 `load_chat` 一次，不管队列是否为空，任务也不回收。长会话多了以后会让流式输出周期性卡顿，没有测量。
- 设置抽屉的会话页草稿在打开时复制，含 `longTermMemory`。抽屉开着时助手或自动总结更新了长期记忆，再点保存会把旧记忆写回。
- `api/sse.ts`：连接在没有 `done` 或 `error` 事件的情况下断开时，`postAndConsumeSse` 正常返回，调用方按成功处理并从服务器重载，本地的半截回复消失且没有任何提示。

## 第三轮：助手和 TTS（2026-11-11）

### 9. 没开破坏性开关时，助手仍能清空工作区文件（已确认）

- 现象：`allow_destructive_tools=False` 时，`workspace_replace_character_card` 和 `workspace_delete_file` 被拒绝，角色卡草稿不变（对照）；`workspace_write_file` 对同一个 `character_card.json` 写入空内容成功，文件变成 0 字节。
- 原因：`assistant_tools/handlers/workspace.py` 的 `handle_workspace_write_file` 直接覆盖已有文件，不检查开关；`workspace_create_file` 才拒绝已存在的文件。
- 作者决定（2026-11-11）：覆盖已有文件算破坏性操作，要开关。写新文件不受影响。未修。

### 10. 不带 `chatId` 的助手重置会删掉所有会话的助手附件（已确认）

- 现象：两个会话各有一个助手附件。`POST /api/assistant/reset?chatId=甲` 只清甲（对照）；`POST /api/assistant/reset` 不带参数时两个会话的附件都被删。
- 原因：`routes/assistant.py` 的 `reset_assistant` 在 `chatId` 为空时调用 `clear_assistant_chat_attachments(None)`，后者把整个 `ingest/assistant_chat` 目录删掉。
- 影响：前端的 `resetChat` 只在有会话时才发请求，界面上目前触发不到，是接口层面的隐患。

### 11. TTS 缓存文件名直接用请求里的音频格式（路径行为已确认，接口未实测）

- `routes/tts.py` 的 `SynthesizeReq.audio_format` 是不设限的字符串，MiniMax 平台把它原样放进结果的 `format`，再拼成 `{asset_id}.{format}` 写入缓存目录。
- 实验只验证了路径行为：在 Windows 上向 `缓存目录/abc123.mp3/../../escaped.bin` 写入会成功，文件落在缓存目录之外（`data/` 下）。没有搭模拟 TTS 上游走完整接口。
- 修法：格式用白名单。

### 自动总结长期记忆被下一条回复覆盖（第 1 项的现实触发路径，读代码）

- 自动总结在回复结束后由助手执行，要跑几秒到几十秒；`ChatPage.vue` 的发送只检查主聊天的 `isGenerating`，不管助手是否在运行。
- 所以总结还没写完时发下一条消息，助手的长期记忆写入落在新回复的流式期间，回复结束时被第 1 项的整份回写删掉。
- 接着 `maybeTriggerAutoMemorySummary` 里更新 `lastAutoMemorySummaryAfterMessageId` 的 PUT 也会被回滚，下次会对同一段对话再总结一次。
- 第 1 项的机制已实验确认，这条具体路径没有单独复现。

### 多会话同时生成：助手和延后操作

读代码得出，未做实验：

- 助手状态每个作用域只有一份（`useAssistant.ts`），切会话不会中止正在运行的助手。`buildPath` 取的是调用当时的 `chatId`，所以在甲会话启动助手、切到乙之后再停止，半截回复会存进乙的助手记录；结束时加载的也是乙的记录。
- 自动总结结束时如果当前会话已不是发起的那个，`maybeTriggerAutoMemorySummary` 直接返回，不更新锚点，下次重复总结。
- 助手写入长期记忆后推送整份会话，`applyChatPayload` 用它替换 `activeChat`；主聊天此时在流式输出的话，本地气泡会像第 4 项那样消失。
- 切会话时 `clearGenerationDeferState()` 清掉了重写和“保存并发送”的延后删除上下文；原会话的生成结束后，本该删除的旧尾部消息不会被删。

### 其他（读代码）

- 助手记录里出现“带 `tool_calls` 的助手消息后面没有工具结果”时没有修复逻辑（`_assistant_messages_to_openai`）。中断只可能发生在联网工具执行期间或进程崩溃，之后上游会拒绝这段历史，要重置助手才能继续。
- `GET /api/tts/audio/{id}` 每次请求都遍历整个缓存目录找文件；缓存清理按修改时间删旧文件，不看最近是否播放过。

## 第四轮：会话列表、TTS 播放队列、完整性巡检（2026-11-11）

### 12. MVU 状态表较大时，群聊从群聊列表里消失，更新时间也读错（已确认）

- 现象：群聊有十几条消息（文件前 4KB 之后才是会话自己的字段）时，状态表 5 行和 60 行正常（对照）；120 行（状态约 22KB）和 240 行时，`GET /api/chats/groups?summary=1` 不再返回这个群聊，摘要里的 `updatedAt` 也和真实值不一致。
- 原因：`storage.py` 的 `read_chat_list_meta` 不解析 JSON，只取文件开头 4096 个字符和末尾 16384 字节用正则找字段。`Chat` 的字段顺序是 `messages`、`overrides`、`isGroup`、`memberIds`、…、`updatedAt`、`stateVariables`、分叉字段，`stateVariables` 一旦超过约 16KB，`isGroup`、`memberIds`、`updatedAt` 就落在两段之外。
- 单聊同样受影响：`updatedAt` 找不到时退回当前时间，这个会话每次都排在最前，选角色时会被当成最新会话打开。这一点是按代码推出的，实验只测了群聊。
- 这种写法对以后在 `stateVariables` 之后或之前加字段都很敏感。

### 13. TTS 合成失败的条目留在播放队列里，这条消息之后手动朗读没有反应（机制已验证，界面未走）

- `useTtsPlaybackQueue.ts` 的 `enqueue` 把原始对象 `push` 进 `ref` 数组，再把同一个原始对象交给 `downloadItem`。失败时用 `queue.value.findIndex((i) => i === item)` 找它来删除，但数组里取出来的是响应式代理，和原始对象不相等。
- 单独用 Vue 验证：这个 `findIndex` 返回 -1，条目没被删；对照 `indexOf(item)` 返回 0。
- 后果（读代码）：条目以 `error` 状态留在队列里。`ChatPage.vue` 的 `enqueueMessageReadAloud` 把“队列里已有这条消息且状态不是 done 或 aborted”当作重复点击忽略，所以这条消息合成失败一次后，再点朗读没有反应，直到停止全部或刷新页面。队列面板也会一直显示这条失败项。

### 读代码、未复现

- TTS 播放顺序：`playNext` 取队列里第一个 `ready` 的条目，不等前面还在合成的。群聊里几条回复同时合成时，后面的先合成完就会先播。
- TTS 队列里播完的条目（`done`）不出队，只在界面上过滤掉，一次会话里会一直累积。
- 完整性巡检的“修复”对会话记录是直接删除 `chat.json`（`services/data_integrity.py` 的 `_REPAIR_ACTIONS`），不留备份，也不更新会话路径索引和分叉索引，会话目录里的图片和记忆文件留在原地。运行时加载失败（完整 Pydantic 校验不过）的会话也会进这个列表，所以如果某个版本的校验写错了，内容完好的会话会被列为可修复，点修复就删掉了。建议改成移到隔离目录。
- ZIP 导入：角色和会话按 id 直接覆盖本地同 id 的文件，世界书遇到同 id 则另起新 id。把旧备份导进正在用的数据目录时，备份之后新写的对话会被旧版本覆盖，没有提示。
- 会话摘要里 `createdAt` 只在文件开头 4096 个字符里找，而它排在 `messages` 之后，稍长的会话都找不到，摘要的创建时间为空后退回当前时间。

## 第五轮：消息版本、身份切换、用量计价、知识图谱、流式解析（2026-11-11）

### 14. 编辑有多个版本的消息，改动保存不住（已确认，界面复现）

- 现象：角色有两条开场白时，会话第一条消息显示 1/2。点“编辑”把内容改成别的再点“仅保存”，气泡先显示新内容，随后变回原来的开场白；刷新后也是原来的内容。对照：同一角色下没有多版本的开场白，编辑后重新读取是新内容。
- 原因：编辑只发 `{role, content}`，不带版本列表。后端 `update_message` 把新内容写进了 `content`（磁盘上的 `chat.json` 里确实是新内容），但版本列表 `greetingVariants` 没动。之后每次读取会话，`storage.py` 的 `_sanitize_chat_greeting_variants` 发现 `content` 不在版本列表里，就把 `content` 改回第一个版本，下标也重置为 0。
- 影响范围：多开场白的第一条消息，以及重写过、带两个以上版本的回复。编辑前如果停在第 2、3 个版本，编辑后还会跳回第 1 个版本。发给模型的也是被改回去的内容。
- 前端 `handleSaveEditedMessage` 其实调用了 `updateCurrentVersionContent` 更新内存里的版本，但保存请求没有带上，所以服务端不知道。

### 15. 切换身份并继续对话时，更早身份发的消息被改成上一个身份（已确认，界面复现）

- 现象：三个没有头像的身份 PA、PB、PC。会话里有一条 PA 发的消息和一条 PB 发的消息，当前身份是 PB。切到 PC 并选“仍然继续对话”后，PA 那条消息的发送者在数据里变成了 PB，刷新后界面上也显示 PB。弹窗里写的是“历史消息会保持原身份显示”。对照：两条消息都带头像快照的会话，同样操作后发送者不变。
- 原因：`useChatActions.ts` 的 `freezeUserMessagesSenderSnapshot` 把“名字、头像、身份 id 三者缺任何一个”的用户消息都当成还没固化，用当前身份重写一遍。身份没设头像时，头像快照永远是空的，所以每次切换都会把之前所有用户消息改成切换前的那个身份。
- 另外两点（读代码）：它对每条用户消息单独发一次请求，每次请求后端都读写整份会话并返回整份会话，长会话切换身份会很慢；切换后界面上的名字在刷新前不变，和数据不一致。

### 16. 删除一个没在用的身份，当前身份会被换成列表第一个（已确认，界面复现）

- 现象：身份列表 PA、PB、PC，当前是 PB。删除 PC 后，当前身份变成 PA。
- 原因：`useChatActions.ts` 的 `deletePersona` 无条件写 `selectedPersonaId: personas[0]?.id`，注释写的是“如果删除的是当前选中身份才换”。

### 17. 本地估算费用时，缓存命中的输入被算了两次（已确认）

- 现象：同一次调用（100 个新输入、900 个缓存命中），按 Anthropic 的用量格式估算结果正确（对照）；按 OpenAI 兼容格式估算是正确值的 5.74 倍。
- 原因：OpenAI 兼容、OpenAI Responses、Gemini 三个适配器把上游的输入总数（已含缓存命中部分）原样当作 `inputTokens`，`pricing.py` 的 `estimate_cost_from_usage` 再按“输入 × 输入单价 + 缓存读 × 缓存单价”相加。Anthropic 的输入数不含缓存，所以只有它是对的。
- 同一个口径问题也影响缓存命中率（`usage_ledger.py` 用“输入 + 缓存读”做分母），这三种协议下命中率会偏低。命中率这一点是读代码得出的。
- 上游自己返回费用时不受影响，只影响本地估算。缓存命中率越高，估算偏差越大。

### 18. 知识图谱注入深度设成 0，实际按 5 处理（已确认）

- 现象：深度 1、2 时注入块后面分别有 1、2 条消息（对照）；深度 0 时后面有 5 条。
- 原因：`kg_inject.py` 的 `resolve_inject_depth` 写的是 `int(depth or 5)`，0 被当成没填。界面和保存接口都允许 0。

### 19. OpenAI 兼容流式解析遇到 `choices` 为空的帧就报错中断（已确认，是否算问题待定）

- 现象：正常流能读出正文（对照）；在最前面加一帧 `{"choices": [], "prompt_filter_results": [...]}` 后，报“上游流事件缺少 choices”，整次生成失败。
- Azure OpenAI 的流式响应第一帧就是这个形状，一些中转站也会发空 `choices` 的帧。现在的解析只放过“空 `choices` 且带 `usage`”的帧。
- 这是有意的严格解析还是遗漏，需要作者定。如果要接 Azure 或这类中转，这里得放宽。

### 读代码、未复现

- 版本切换（点左右箭头）只记在内存里的 `pendingGreetingVersion`，到下次发送、重写或切会话时才写盘。切完直接刷新或关页面，切换不保留。
- `hydrateGreetingVariants` 会先去掉空的版本再按原下标取思考内容和耗时，而中断时合入的版本允许“正文为空、只有思考”，这种情况下后面各版本的思考内容会错位一格。
- `cleanupVersions` 裁剪了正文和思考数组，没有裁剪耗时数组，裁剪后留下的是第 1 个版本的耗时。
- `saveVersion` 按正文是否相同去重，两次重写出完全相同的正文会被并成一个版本。
- 用量账本写入失败时 `append_usage_event` 抛 500，而它在会话保存之后调用：回复已经存好，前端却收到失败。只在磁盘写不进时出现。
- 用量分片按本地时间的月份命名，筛选时按 UTC 的月份边界跳过分片。带 `until` 参数查询时，月初头几个小时（东八区是 0 点到 8 点）的记录可能被漏掉。界面目前只用 `range`，不触发。
- 设置备份 ZIP 里的 `settings.json` 只隐去 Vertex 服务账号私钥，普通 API Key 是明文。作为备份是合理的，但“含角色”这一档容易被当成分享包发给别人；是否要在导出时提示，需要作者定。
- ZIP 导入遇到 `settings.json` 会整份覆盖当前设置。结合第 6 项（其他网页可以向 `/api/import` 提交文件），等于其他网页能替换全部设置，包括把接口地址指到别处。
- OAuth 的 PKCE 回调如果只粘贴 code 不带 state，会跳过 state 校验；`llm/runtime.py` 的 `list_models` 用 `except TypeError` 做兼容，会把适配器内部真正的 `TypeError` 吞掉再重试一次。两处影响都很小。

## 第六轮：重写和“保存并发送”（2026-11-11）

### 20. 群聊里“保存并发送”之后点“下一轮”，被隐藏的旧回复没有删除，还会发给模型（已确认，界面复现）

- 复现：群聊（Tester、Bee）里有一条用户消息和两条旧回复。编辑用户消息点“保存并发送”，两条旧回复从界面消失。接着点“下一轮”。
- 结果：模拟上游收到的上下文里仍有两条旧回复；磁盘上旧回复还在，新回复排在它们后面；界面上旧回复一直隐藏，刷新页面后重新出现。
- 对照：同样的步骤，改点“让 Tester 单次回应一条”，上下文里没有旧回复，磁盘上旧回复已删除。
- 原因：群聊的“保存并发送”（`ChatPage.vue` `handleSaveAndSend`）只把尾部消息登记为“延后删除”并隐藏，真正的排除和删除只写在 `triggerInterject` 里。“下一轮”、继续、直接发新消息这几条路都不读这份登记，也没有地方清掉它。切到别的会话再回来，隐藏状态同样还在。

### 21. 重写中间的一条回复时，上游只返回空白字符，后面的消息被全部删除，没有任何提示（已确认，界面复现）

- 复现：会话为 问1、答1、问2、答2。模拟上游返回只含空格和换行的流。对“答1”点重写。
- 结果：没有报错，“答1”原样不变、没有新版本，“问2”和“答2”从磁盘上删除。
- 对照一：上游返回 500 时报错，后面的消息保留。对照二：上游返回完全空的流时，适配器报“上游流未返回任何有效内容”，后面的消息保留。
- 原因：后端把正文去掉首尾空白后为空时，不写消息但仍返回 `ok: true`（`generate.py` 流式约 1647 行，非流式同理）。前端只按“有没有报错”决定是否删尾部（`finalizeRewriteAfterGeneration`），没有检查这次重写是否真的产生了新版本。
- 单聊的“保存并发送”走同一个判断：空白回复时尾部也会删掉，且没有新回复。那里用户本来就要截断，损失小一些。

### 读代码、未复现

- 单聊“保存并发送”不带合并目标，后端把新回复追加在旧尾部之后，前端再逐条发请求删旧尾部。生成结束到删完之间关掉页面，磁盘上会留下“旧尾部加新回复”。后端已有一次完成的 `save-and-truncate` 接口，前端 `saveAndTruncate` 没有任何调用方，是闲置代码。

- 重写的非流式分支没有带发送者快照字段，流式分支带了；`appendUserMessage` 为 false 时后端大概用不到，没有验证。
- 重写和“保存并发送”结束时同样会 `chats.load(chatId)`，属于第 3 项（切走后被拉回）的同一类。
- 设计如此、不算问题：发出新消息后，所有回复的备选版本会被清掉；重写一条回复会清掉其他回复的备选版本（`_clear_greeting_multivariant_on_other_assistants`）。界面上没有说明这一点，是否要提示由作者定。

## 第七轮：导入导出（2026-11-11）

实验脚本为进程内调用，数据目录是临时目录。

### 22. 把 JSONL 或 TXT 导出的会话再导入本机，原会话被精简版整份覆盖（已确认）

- 复现：会话带会话级预设、长期记忆，回复带思考内容。导出后原样导入。
- 结果：JSONL 和 TXT 两种格式导入后，同一个会话的预设变为空、长期记忆被删、思考内容丢失。对照：JSON 格式导出再导入，会话不变。
- 原因：JSONL / TXT 只导出 role、name、content，但文件头带原会话的 `chatId`；导入时用这个 id 新建一个只有正文的会话并 `save_chat`，直接盖掉原文件（`_import_from_jsonl`、`_parse_chat_text`、`_build_chat_from_transcript_rows`）。`save_chat` 在没有长期记忆时还会删掉 `chat_memory.json`。图片、MVU 状态表、消息版本等同样丢失。
- 导入接口没有“已存在同 id 会话”的提示或另存为新会话的分支。

### 23. TXT 导出的正文里有单独一行 `>>>` 时，再导入会在这一行截断（已确认）

- 正文为三行、中间一行是 `>>>`：导出再导入后只剩第一行。对照：普通三行正文完整保留。
- 原因：TXT 格式用 `<<<` / `>>>` 包正文，导出时不转义（`_export_chat_text`），解析时遇到第一个 `>>>` 就结束（`_parse_chat_text` 的 `read_block`）。`>>>` 在引用别人消息或贴 Python 交互记录时会出现。结合第 22 项，截断后的内容会盖掉原会话。

### 24. 同一份备份 ZIP 导入两次，世界书每次多一份，角色改挂到副本上（已确认）

- 复现：1 本世界书挂在角色 Alpha 上，导出“含角色”备份，连续导入两次。
- 结果：世界书 1 → 2 → 3 本；角色数不变（对照，角色按 id 覆盖）；Alpha 挂的世界书从原来那本变成了新副本。

- 用备份在本机“恢复”是这个功能最直接的用法，结果是世界书成倍增加。是覆盖还是另存，需要作者定。

### 25. 重名角色：JSONL / TXT 导入的会话可能落到另一个同名角色下，出现两个同 id 的会话（已确认）

- 两个角色都叫 Twin。其中一个角色的会话导出 JSONL 再导入后，磁盘上出现两份同 id 的 `chat.json`，分别在两个角色目录下。另一个角色的会话导入后仍只有一份（对照）。

### 26. 酒馆卡世界书的关键词导入后区分大小写；多个正则关键词拼接后失效（已确认）

- 关键词 `Dragon`：导入后的规则是 `Dragon`，正文里的 `dragon` 不触发。对照：关键词 `dragon` 能触发。酒馆里关键词匹配默认不区分大小写（这一点是我凭对酒馆的了解说的，没有对着酒馆实测）。
- 两个正则关键词 `/wyrm/i`、`/drake/i`：导入后拼成 `/wyrm/i|/drake/i`，不再被识别为 `/…/i` 写法，正文 `WYRM` 不触发。对照：只有一个 `/wyrm/i` 时能触发。

- 位置：`_st_entry_regex`（`import_export.py`，`routes/avatars.py` 里还有一份相同的实现）。`secondary_keys`、`selective` 等酒馆字段没有处理（读代码）。

### 已排除

- JSONL、TXT、JSON 三条导入路径里来自文件的会话 id 含 `../` 时，都被拒绝并返回“会话 id含有非法路径字符”，没有写到数据目录之外（已实测，对照为普通 id 正常导入）。

## 第九轮：Anthropic、Gemini、Responses 适配器（2026-11-11）

实验用本地模拟上游按各协议的流格式应答，直接调用适配器，不涉及应用数据。没有连真实上游。

### 32. 纯 AI 模式和按深度注入的内容，在 Anthropic / Gemini / Responses 上位置全部丢失（已确认）

- 输入：角色卡（system）、第 1 轮（system）、回复 1（assistant）、第 2 轮（system）。纯 AI 模式下用户的每一轮就是 system 角色（`generate.py` 约 660、668 行）。
- 对照：OpenAI 兼容协议原样发出四条，顺序不变。
- Anthropic：system 变成“角色卡、第 1 轮、第 2 轮”拼在一起，对话只剩 `user "."` 和 `assistant 回复 1`，以助手消息结尾。
- Gemini：`systemInstruction` 同样三段拼接，`contents` 只剩一条 model 消息。Responses：`instructions` 三段拼接，`input` 只剩一条 assistant 消息。
- 原因：三个适配器的消息转换都把所有 system 消息抽到顶层（`_convert_messages` / `_convert_input`），不管它在对话里的位置。
- 受影响的不只纯 AI 模式：世界书按深度注入（`generate.py` 约 936 行）、知识图谱按深度注入（`kg_inject.py` 93 行）、MVU 状态表注入都是插在对话中间的 system 消息，在这三个协议上都会跑到最前面，“深度”设置不起作用。
- 模型实际怎么回应没有测（没有连真实上游）。以助手消息结尾的请求，Anthropic 会当作续写，部分新模型会直接拒绝，这一点是凭对接口的了解说的。
- Bedrock Converse 和 Mistral 适配器里也有对 system 角色的单独处理（`bedrock_converse.py` 234 行、`mistral_conversations.py` 160 行），没有细读，可能是同一种情况。

### 33. Gemini 流式思考内容的分片被逐片去掉首尾空白，词和段落粘在一起（已确认）

- 思考内容分三片到达：`Hello `、`world.\n\n`、`Next step`。得到的思考文本是 `Helloworld.Next step`。对照：同一个流里正文分片 `Body `、`text` 得到 `Body text`，空格保留。
- 原因：`_extract_text_thoughts_and_tool_calls` 末尾对思考内容做了 `.strip()`，流式时每一片都会走这个函数。英文思考会丢空格，中文思考会丢段落换行。

### 34. Responses 协议下回复因长度上限被截断时，整条回复按失败处理（已确认）

- 流里先有正文增量，然后是 `response.incomplete`（原因 `max_output_tokens`）：适配器抛出“OpenAI Responses 请求未成功完成”，此前已收到正文。
- 对照：Anthropic 的 `stop_reason=max_tokens` 正常结束并保留正文；Responses 正常 `response.completed` 也正常结束。
- 后果（读代码）：生成接口走错误分支，不保存这条回复；已经显示出来的半截内容在重新读取会话后消失。达到长度上限是常见情况，其他协议下都能留下已生成的部分。

### 35. Gemini 流在没有结束标记的情况下断开，被当作正常完成（已确认，影响小）

- 流里只有一片正文、没有 `finishReason` 就结束：适配器返回成功。对照：Anthropic 流缺 `message_stop` 时报“响应流提前中断”。
- Responses（缺 `response.completed`）和 OpenAI 兼容也都有类似检查，只有 Gemini 没有。连接被中转站正常关闭但内容不完整时，半截回复会被当成完整回复保存。

### 读代码、未复现

## 第十三轮：TTS 各平台合成和本地进程管理（2026-11-12）

范围：`services/tts_platform.py` 里 MiniMax、GLM（云端）、OpenRouter / 硅基流动、三个本地平台的合成路径，`routes/tts.py` 的 `/synthesize`，`*_local_tts_process.py` 的启动逻辑。实验用本地模拟上游经 `/api/tts/synthesize` 走完整路径，没有连真实的 TTS 服务，也没有启动任何本地 TTS 进程。流式合成路径（`synthesize_stream`）前端目前不用（请求固定 `stream: false`），只读了代码。

### 41. GLM（云端）朗读超过 1024 字的内容被截断，没有任何提示（已确认）

- 实验：2800 字的文本经 GLM 预设合成，上游只收到前 1024 字；接口返回成功，`warnings` 为空，`partialSuccess` 为 false。
- 对照：800 字原样送达；同样 2800 字经 MiniMax、硅基流动预设，上游收到完整的 2800 字。
- 原因：`GlmTtsPlatform._clamp_text` 截到 1024 字，只写一条后端日志。前端把整条消息作为一次请求发出（`useTtsPlaybackQueue.downloadItem`），不分段。
- 后果：长回复只读出开头一段就结束，看起来像是读完了。MiniMax 有同样写法的 10000 字上限（`_build_t2a_body`），一般回复碰不到。

### 42. MiniMax 预设填“完整 TTS 接口地址”时路径被拼重（已确认）

- 抽屉里 MiniMax 的地址提示写的是“兼容基础域名、/v1、或完整 TTS 接口地址”。
- 实验：地址填 `…/v1/t2a_v2`，后端实际请求的路径是 `/v1/t2a_v2/t2a_v2`。
- 对照：填基础域名或 `…/v1`，请求路径都是 `/v1/t2a_v2`；GLM 填完整的 `…/api/paas/v4/audio/speech`，请求路径正确。
- 原因：`_normalize_minimax_api_base` 只会剥掉 `/chat/completions`，不认识 `/t2a_v2`。

### 43. MiniMax 合成失败时看不到上游给的原因（已确认）

- 实验：上游返回 401 并在响应体里说明原因。经 MiniMax 预设，返回给前端的是 httpx 的通用英文信息 `Client error '401 Unauthorized' for url …`，上游的说明丢了。
- 对照：同一个 401 经 GLM、硅基流动预设，返回的是上游的说明文字。
- 原因：MiniMax 的合成路径直接 `resp.raise_for_status()`，没有像另外两个平台那样先读响应体里的错误信息。

### 44. 上游用 200 状态返回 JSON 错误时，错误文本被当成音频存进缓存（已确认，是否会遇到取决于上游）

- 实验：上游对合成请求返回 200，内容是一段 JSON 错误。经 GLM、OpenRouter、硅基流动预设，接口都返回成功和一个音频 id，取回的“音频”内容就是那段 JSON。
- 对照：MiniMax 预设在同样情况下报“返回空音频数据”。
- 原因：这三条路径只检查状态码和内容非空，不看响应的内容类型。OpenRouter / 硅基流动在内容类型认不出时退回到请求的格式（mp3）。
- 真实的官方接口是否会这样返回没有验证；经中转站时更可能出现。后果是这条消息朗读没有声音也没有报错，而且这个坏文件会被绑定到消息上。

### 读代码、未复现

- OmniVoice（本地）的参考音频路径不存在时只写一条日志，然后改用指令音色或自动音色合成，不报错；GLM 本地和 Qwen3 本地在同样情况下会报“参考音频不存在”。结果是音色悄悄变了。同一条音色既填了参考音频又填了指令时，指令被丢弃。

- Qwen3（本地）开了托管启动时，每次合成都要求主模型和克隆用的 Base 模型两个进程都就绪，即使这条音色不用克隆；两个模型同时占显存。属于设计取舍。

## 第十四轮：提示词缓存（2026-11-12）

范围：`llm/prompt_cache.py`（缓存计划和各协议写法）、`llm/gemini_cache_store.py`（Gemini 显式缓存索引），以及 Anthropic、Gemini 适配器里使用它们的位置。实验用本地模拟上游，没有连真实服务；费用方面的结论都是按各家公开的计费规则推断的，没有实测账单。

### 45. 纯 AI 模式或按深度注入的内容有变化时，显式缓存每一轮都重写、从不命中（已确认机制，费用为推断）

这是第 32 项的连带后果：三个协议把所有 system 消息抽到最前面，而缓存断点正好打在这一块上。

- Anthropic（显式缓存，断点在 system）：同一会话连续两轮，带 `cache_control` 的那一块文本是否相同。
  - 对照：普通会话两轮相同。
  - 纯 AI 模式：不同（每一轮的用户输入都被拼进了 system）。
  - 世界书触发的条目在两轮之间变化：不同。
- Gemini（显式缓存）：同一会话连续两轮创建了几个 `cachedContents`。
  - 对照：普通会话 1 个，第二轮复用。
  - 纯 AI 模式：2 个。世界书条目变化：2 个。也就是每一轮新建一个。
- 推断的后果：Anthropic 的缓存写入比普通输入贵，每轮都写、从不读，等于开了缓存反而更贵；Gemini 每个 `cachedContents` 按存活时间计存储费，默认存活 1 小时，每轮新建一个，旧的没人用也要存满时间。
- Anthropic 协议在“自动”模式下默认就是显式缓存（`build_prompt_cache_plan`），所以不需要手动打开就会走到这条路径；Gemini 要手动选显式才会。
- 本地索引 `data/llm_cache_index.json` 只增不减（实验里 3 组各两轮之后有 5 条），代码里没有按存活时间清理的逻辑。

### 读代码、未复现

- Gemini 缓存在上游过期或被清掉后，适配器只在收到 404 时丢弃索引并重建。实验里 404 确实能自动恢复；如果上游返回的是 403，会被当成“鉴权失败”，索引不清，同一系统提示词的后续请求一直失败（实验里连续两次都失败）。真实接口对失效缓存返回哪个状态码我没有查到官方说明，搜到的一篇第三方文章说是 404，并且提到缓存可能在存活时间到期前就被清掉。所以这条是否成立取决于上游。
- Gemini 缓存索引的指纹只含模型、系统提示词、工具，不含 API Key 和接口地址。两个预设用不同的 Key、相同的模型和系统提示词时，会共用一条索引，后者拿到的是前者账号下的缓存名。
- Gemini 显式缓存在创建前不检查内容是否达到最小长度（计划里算了 `min_tokens` 但没有用来拦截）。系统提示词太短时上游会拒绝创建，按代码这次回复直接失败；文件头注释写明“创建失败必须报错，不得静默退回无缓存”，属于有意设计，但短角色卡加显式缓存会每次都失败。
- `is_openai_official_host` 用“主机名以 … 结尾”判断，`chatgpt.com` 没有带点，`notchatgpt.com` 这类主机会被当成官方；主机名带端口时又会判成非官方。只影响是否发送 `prompt_cache_*` 字段。
- Anthropic 的默认断点只有 system，历史消息不缓存，除非手动加“历史末尾”断点。长对话里真正占大头的是历史，这是设计取舍，记一笔。

### 46. Gemini 协议选“独立搜索”时，模型发出的搜索请求被适配器丢掉，回复直接失败（已确认）

  - 流式：只发了 1 次请求，报“上游流未返回任何文本”，没有执行搜索。
  - 非流式：报“上游服务返回了空消息”。
  - 对照：同一个解析函数，调用名换成 `web_fetch` 时正常返回工具调用。
- 界面上这条路是明确提供的：Gemini 模型打开联网后，输入框旁可以选“原生 / 独立”。选“独立”后，只要模型决定搜索就会失败；模型同时输出了文字时不会报错，但搜索不会发生。

  - 第二轮请求仍然带着 `thinking: enabled`，但助手那一轮的内容块只有 `text`、`tool_use`，整个请求里找不到签名。
  - 对照：把原始内容块传给同一个适配器（助手面板就是这么做的），得到 `thinking`、`tool_use`。
- 按 Anthropic 的文档，开启思考并使用工具时，上一轮的思考块必须原样带回，否则请求会被拒绝。这一点我没有对真实接口验证，所以后果写成“很可能每次搜索后的第二轮都失败”。
- Gemini 的思考签名（`thoughtSignature`）在代码里完全没有出现，独立搜索修好之后会遇到同类问题。只读了代码。

### 50. 点“重写”后，输入框里没发出去的内容被换成上一条提问（已确认，界面）

### 51. 对不是最后一条的回复点“重写”，那条回复被删掉，新回复接在整段对话末尾（已确认，界面）

- 操作：两轮对话（提问 1、回复 1、提问 2、回复 2），点回复 1 的“重写”。
- 结果：面板里变成“提问 1、提问 2、回复 2、新回复”，提问 1 没有回复了，末尾连着两条助手回复。发给上游的内容是“提问 1、提问 2、回复 2”，以助手消息结尾。
- 对照：只有一轮对话时点“重写”，旧回复被新回复替换，正常。
- 原因：重写只删掉被点的那一条，然后让后端按现有的全部记录再生成一次；后端在不追加用户消息时不看传过去的提问文本。

### 52. 删除“带工具调用的那条回复”后，工具结果成了孤儿，照样发给上游（已确认请求内容，上游是否拒绝未验证）

  - 动作是“提取”的规则：文本原样返回。也就是说提取类规则在试运行里看不到任何效果。

  - 写错的规则 `(`：原样返回，没有任何报错。

### 64. 前端的规则超时不起作用，回溯爆炸的规则会卡住页面（函数级确认）

- 在页面里直接调用显示函数，规则 `(a+)+$`：20 个 `a` 加一个 `b` 用 23 毫秒，22 个 91 毫秒，24 个 350 毫秒，每多两个字符耗时变成 4 倍。对照：规则 `a+b` 是 0 毫秒。设定的超时是 150 毫秒。

### 扩展依赖网站的哪些东西（任何一项变了都会失效）

- 聊天导入（`injected.js` 截获网页自己的请求）：
  - 只看地址最后一段是纯数字的 fetch / XHR 请求，比如 `…/chats/12345`。网站换了接口路径（加版本号、改成非数字 id、改走 GraphQL 或 WebSocket）就一条都截不到。
  - 响应必须是 JSON，顶层有非空的 `chatMessages` 数组。
  - 后端再从里面取：每条消息的 `is_bot`、`created_at`（用来排序）、正文 `message`（字符串或数组）/ `content` / `text`；角色名取 `character` 里的 `chat_name`、`name`、`character_name`、`displayName`。
- 角色导入首选路径：读网页里的全局变量 `window.mbxM`，找名字以 `characterStore` 结尾的键，取 `.character`，要求有 `first_message` 或 `first_messages`。`mbxM` 看起来是打包工具生成的名字，网站重新构建一次就可能改名，这是最脆弱的一处。
- 角色导入后备路径（5 秒内没拿到上一条时）：
  - 等页面上 `[class*="viewCharacterSkeleton"]` 消失、出现 `img.avatar-image` 且地址含 `bot-avatars`，最多等 60 秒。
  - 然后把整页 HTML 交给后端，后端用正则找 `window.mbxM.push(JSON.parse(`、`characterInfoAccordionItem_`、`id="info-数字"`、`<title>` 等标记。
- 网址：只在 `janitorai.com` 及其子域名上运行。

### 读代码时顺带看到的问题

- 扩展把数据发给哪个后端，用的是扩展自己的设置，缺省是 `http://127.0.0.1:9091`；导入弹窗通过网址参数告诉它的只有前端地址，没有后端地址。所以从 9081 以外的实例（比如测试实例）发起导入，数据仍然送到 9091 那个实例，回跳的页面却是发起的那个实例，那边找不到这份待导入数据。
- 聊天截获只认第一个合格的响应。如果网站先加载最近一页、滚动时再加载更早的，导入的只是最近一页。没有验证网站是不是分页加载。
- 消息正文是数组时（推测是多个候选回复），取的是最后一个非空的，不一定是用户当时选中的那个。这是对字段含义的推测。

### 65. 分叉出来的会话丢失“绑定到本会话”的世界书（已确认）

- 原因：会话世界书的绑定记在世界书自己的 `sessionChatIds` 里，分叉时只复制了会话的设置（`overrides`），没有把新会话的 id 加进这些世界书。

- 同样不复制的还有长期记忆（有意清空，代码注释写明）和 MVU 状态（`stateVariables` 置空，接口注释写明不复制）。MVU 状态不复制意味着分叉后状态从初始值重来，而不是分叉点当时的状态。作者已确认（2026-11-12）这是想要的行为，不算问题。

  - 对照：网络面板里看到前端确实请求了源会话的分叉信息，后端返回的结果里，第 2 条消息下有 2 个分叉。

### 67. 分叉索引出过一次问题后，“分叉索引损坏”的提示就一直弹（已确认）

- 实验：把 `fork_index.json` 写坏一次。之后连续两次请求分叉信息都带着 `fork_index_corrupt` 警告；改一次会话标题、再分叉一次之后，查另一个分叉会话，仍然带着这条警告。对照：写坏之前没有警告。
- 原因：重建索引时把这次的警告存进了索引文件，之后的每次保存都原样保留；只有再次重建才会清掉，而重建只在索引又坏了、或删除整个角色的会话时发生。
- 前端每拿到一次分叉信息，就把警告推到右下角的错误提示里（`onWarning`）。也就是说，打开任何一个分叉会话都会弹“分叉索引提示：分叉索引损坏，已从会话文件重建”，实际上索引早就修好了。

### 68. 分叉索引重建后，分叉的创建时间全部变成空的（已确认）

- 实验：同一条消息分出两个会话，删掉索引文件让它重建。重建前兄弟分叉的创建时间正常；重建后全部为空字符串，源会话的分叉列表里也都是空的。
- 原因：重建时用正则从会话文件开头 4096 字符里找 `createdAt`，而会话文件里 `createdAt` 排在所有消息之后，开头根本没有它（`read_chat_fork_meta`）。
- 后果：分叉列表按创建时间排序，重建后顺序变得没有意义。第 67 项那样的情况、以及删除整个角色的会话时都会重建。

### 读代码或实验中看到、影响小

- 删掉源会话里作为分叉点的那条消息（实验确认）：分叉会话的横幅仍写“第 2 条消息”，但源会话的第 2 条已经是另一条了；源会话的分叉记录仍挂在已删除的消息 id 下，界面上无处显示（何况第 66 项本来也不显示）。
- 删掉源会话（实验确认）：分叉会话的横幅显示“分叉自「已删除的会话」”，仍然可以点，点了弹“无法打开源会话”。
- 每次保存任何会话（包括每次发消息）都会读写一次整个 `fork_index.json`。会话很多时这个文件会变大，每次保存都要多做一次整文件读写。没有测量。
- 分叉只记录直接的来源，分叉的分叉在横幅里只能看到上一层。设计取舍。

- `aws_eventstream.py` 的 `EventStreamDecoder.feed` 将当前读取块的帧存入局部列表。后续帧在 `_next_frame` 抛异常会让整个 `feed` 提前退出。外层捕捉错误时拿不到已通过校验的帧，因而没有机会将它们交给适配器。验收时应让同一字节序列在不同读取边界下，都先交付坏帧前已经验证的正文，再终止流。

### 完整帧的大小边界与解码成本
